Executive Summary

DocMind Table-Aware Ingestion and Retrieval Upgrade

The document pipeline was upgraded from text-only retrieval toward a table-aware architecture so financial, comparative, and tabular questions can be answered with materially better structure, traceability, and future LLM readiness.

What Was Solved

Tables are no longer treated only as loose text blobs. The system now detects table-like PDF pages, extracts structured tables, stores them separately, and embeds both text and tables in one retrieval layer.

Why It Matters

This directly improves reliability for numeric lookups, year-over-year comparisons, and document questions where the answer depends on row and column relationships rather than plain keyword matching.

Implemented Changes

  • New table pipeline: Added page-level table detection with confidence scoring and configurable thresholds for every PDF page.
  • Structured extraction: Integrated Camelot-based extraction for detected pages, with validation rules, markdown rendering, normalized numeric values, and full-cell-matrix storage.
  • Dedicated table storage: Added a new document_tables model plus page detection logs and failed-extraction records for observability and debugging.
  • Unified embeddings: Introduced a shared embeddings table so standard text blocks, full tables, and row-level table representations can all participate in semantic search.
  • Async processing queue: Replaced the old per-upload background embedding thread with a queue-backed worker flow that persists jobs and processes embeddings and table extraction asynchronously.
  • Source persistence: Added storage for original PDF bytes so queued workers can access the source document after upload.
  • Context enrichment: Added table provenance capture such as page number, bounding box, and nearby caption or heading text when available.
  • Unified retrieval behavior: Updated retrieval so search can now return either text evidence or hydrated table evidence, including row-level matches plus the full table context.

Business Outcome

  • Creates the core retrieval foundation needed for accurate AI answers on tabular documents without jumping straight into heavy ML layout models.
  • Improves explainability by keeping structured tables, raw markdown, detection scores, and extraction failures available for inspection.
  • Preserves product speed by keeping upload fast and moving expensive embedding and table work into asynchronous processing.
  • Sets up a clean path for the next phase: sending full structured table context into the answer-generation layer.

Current Boundaries

  • The `/ask` route still returns top retrieved evidence directly; full Groq-based answer generation was intentionally left for the next phase.
  • Scanned PDFs are now observable within the pipeline, but Camelot extraction quality will still depend on the underlying PDF structure and may need later OCR-specific handling.
  • Row and full-table embeddings are implemented now; hybrid numeric-intent ranking logic and frontend table rendering were deferred as requested.

Execution Note

  • Focused retrieval tests were updated to match the new unified search behavior.
  • Local executable verification was partially blocked because this machine currently does not expose a working Python launcher and the checked-in virtual environment points to a missing interpreter.
